核心商品系統的服務化與零停機遷移

momo　2025 – 2026

問題

跑了十多年的 JSP / Servlet 單體系統，前後端綁定，前端人力無法參與改版；單一 VIP 映射無法做流量控管；而且是不能停機的核心系統。

做法

先在既有流程加上追蹤，用真實流量找出最常用與最值得改的區塊；以 DDD 劃分模組邊界；導入 APISIX 與 Apollo Config；在舊入口加上開關，新舊流程可隨時切換。

結果

零停機完成第一階段遷移，解除長年技術債，新需求開發與維護時程縮短約 80%。前端人力於 2026 年進場，接手完成前後端分離，驗證了當初提案的判斷。

先有觀測能力，才知道要動什麼；先有回退能力，才敢動。

可觀測性與 DevOps 工具鏈

momo

問題

服務拆分後，問題橫跨多個服務難以定位；日誌只保留一個月，但電商的問題常在數個月後才浮現；回歸驗證仰賴人工。

做法

SkyWalking 與 Elasticsearch 全鏈路追蹤；以 Vector 取代 Filebeat；Parquet 結合 DuckDB 做歷史日誌歸檔；Jenkins、SonarQube、JUnit、Selenium 串成發布前的品質閘門。

結果

跨服務問題可依鏈路定位；單一服務每日約 1GB 的日誌壓縮到約 100MB（省下近九成），得以長期保存並用 SQL 查詢；自動檢核取代每日人工巡視。

中台高頻資料同步與快取防護

momo

問題

高頻的狀態同步，每次都更新同一筆資料，造成資料庫的鎖競爭；查詢不存在的品號會穿過快取直接打到資料庫，無效請求一多，底層負載就跟著上升。

做法

以 Event Sourcing 改為只新增（append-only）的寫入，再聚合出目前狀態；把全量品號預載進 Bloom Filter 當第一道防線，後面接本機快取、Redis 分散式快取與資料庫的多層驗證。

結果

寫入不再互相搶鎖；無效請求在最前面就被擋下，快取穿透的問題消失，資料庫負載大幅下降。

EC 商品共用平台

關貿網路

問題

企業客戶要把商品資料推送到多個外部通路，每個通路的規格都不同，每接一個就是一次客製開發。

做法

完成第一個客戶的串接後，主動向業務提議抽成共用平台：對外提供統一 API，把各通路的差異收在平台內部。

結果

新客戶與新通路只要呼叫同一組 API。整合成本從隨通路數成長，變成一次性的平台投資。

B2B 整合最大的成本不在第一次串接，而在後續每一家的差異都要長期維護。

與業務共同維護的可執行規格

momo

問題

各商品類型的營業額計算規則只存在業務單位的認知裡，每次確認得到的答案不一定一致；寫成文件也會漸漸與程式分岔。

做法

先用 Excel 逐條列出情境與業務對齊，再導入 Cucumber / Gherkin 變成可執行的測試，並寫了 Excel 與 Gherkin 的互轉工具放在 Git 上，業務不必改變工作方式。

結果

業務主動維護規則；QA 當測試案例、PM 用來理解系統、新人拿來當文件。爭議從「當初怎麼講的」變成「規則寫在這裡」。

與其要求對方改變工作方式，不如把工具接到他們原本的方式上。

Kata 社區：多社區住戶服務平台

個人專案　2026

問題

一個平台服務多個社區，每個社區各有成員、公告、行事曆與零用金。權限分平台與社區兩層；重複活動要跨時區、跨日光節約時間都算對；零用金是真的錢，多人同時操作時帳必須對得上，而且要查得到誰改了什麼。

做法

Spring Boot 4 + Vue 3。權限檢查集中在單一入口；重複活動依時區展開，查詢時直接跳到需要的區段；零用金以鎖讓撥補與修改依序執行，並留下只增不改的異動紀錄；活動以版本號防止互相覆蓋。以 Claude Code 協作開發，完成後依 Google L6 標準做全專案 review，分批修正。

結果

後端 67 個測試，包含可重現的並發測試，以及「跳段展開」與「完整展開」的等價測試，並逐一刻意破壞程式，確認測試真的抓得到錯誤。正式環境缺少密鑰時拒絕啟動，登入有多維度的頻率限制。

涉及錢的地方，要隨時答得出「誰、在什麼時候、把什麼改成什麼」。
